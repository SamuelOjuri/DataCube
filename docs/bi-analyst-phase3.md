# Phase 3: isolated API and database access

Implemented 8 October 2026. This is a code delivery and deployment runbook, not a
record of production migration or deployment.

## Assessment and agreed scope

The plan's separation of the API, analytical reader and state writer is sound.
The Phase 2 package gives the API a stable interface without importing ETL startup.
The later 8 October owner decision selects retained reportable projects, including
genuine archived history, instead of API-active eligibility. Catalogue 1.1.0 and
migration 004 retain that population and remove the monthly revenue stage gate.
The catalogue remains `pending_phase1`: deployment/source verification, revised
reference approval and the Order Value mirror chain still need certification. See the
[Phase 2 assessment](bi-analyst-phase2.md). Neither permissions nor passing tests on
synthetic data certify those business definitions.

The owner explicitly requested **skipping authentication for now** during this
implementation. No Supabase sign-in, Microsoft sign-in or token verifier has been
implemented. The trusted identity dependency always returns HTTP 503
`identity_not_configured`. All conversation, run, result, export and resume routes
use that dependency. No header, query parameter or shared anonymous user supplies
identity. Tests inject identities in application code to exercise permissions.
That injection is not exposed through deployment configuration or HTTP.

Consequently the original authenticated Phase 3 exit gate is intentionally open.
Infrastructure readiness can pass while data routes remain disabled. Connecting
real users requires a subsequent identity implementation and its security tests;
running metrics also requires corrected source certification and Phase 4.

## Code and API

The independent package is version 0.3.0. Its entrypoint is
`bi_analyst.api:application --factory`; imports perform no database I/O and do not
import `src`, ETL schedules, Monday consumers, predictions or model adapters.
Pools open and close in the FastAPI lifespan. There are no migration or background
worker actions on startup.

| API | Current behavior after trusted identity is supplied |
|---|---|
| `GET /health/live` | Process health, without identity or a database query |
| `GET /health/ready` | Pool, source permission and state schema checks; explicitly reports deferred identity and unavailable metric execution |
| `POST /v1/conversations` | Creates a user-owned conversation; body contains only `title` |
| `GET /v1/conversations` | Owner-filtered list, `limit` 1–100 and bounded `offset` |
| `GET /v1/conversations/{id}` | Owner-only conversation |
| `POST /v1/conversations/{id}/runs` | Stores the question as `registered`; schedules no execution |
| `GET /v1/conversations/{id}/runs` | Bounded owner-only run history; rechecks permission versions |
| `GET /v1/runs/{id}` | Owner-only stored run |
| `POST /v1/runs/{id}/cancel` | Idempotently cancels a registered run |
| `POST /v1/runs/{id}/resume` | Rechecks owner and permission version, then returns 501 until Phase 5 |
| `GET /v1/results/{id}` | Owner-only persisted result with its columns, rows and provenance |
| `GET /v1/results/{id}/export` | Same authorization; UTF-8 CSV of stored rows, formula-safe string cells; `X-Export-Scope: stored-result-rows` |

There is no result-upload endpoint or arbitrary SQL endpoint. Results will be
written by the trusted query service in Phase 4. The result storage envelope is
bounded to 100 columns, 10,000 rows and 1 MiB of JSON. Full typed metric contracts,
analytical execution limits, checkpoints, streaming and scheduling belong to
Phases 4–5. A registered run must not be presented as queued or executing.

Every scoped request reloads administrator-maintained `principals` and checks
`enabled`, `company_wide` and `permissions_version`. Only complete-company access
is currently supported; partial-scope users are denied. Stored runs/results retain
their permission version; a changed version blocks their retrieval/export/resume.
Cross-user IDs return 404. The application applies owner predicates and PostgreSQL
RLS independently. Transaction-local identity is reset before a pooled connection
is reused. Direct Psycopg connections do not inherit a browser JWT.

Rate limits use an atomic database counter per provisioned user and UTC minute,
shared across replicas. Bodies are bounded before validation, including chunked
bodies. Request IDs are generated by the server, responses use `no-store`, and
validation/database failures omit input and database details. Structured logs
include route templates, status and latency, not prompts, tokens, datasets, SQL or
raw URL paths. Trusted-identity requests append durable audit records, including
denials; audit failure prevents release of a data response. Calls rejected before
identity exists are recorded in structured logs only. Retention automation remains
Phase 7; the runtime cannot delete audit records.

## Option A and database roles

Updated 8 October 2026 following the owner's Option A decision and approval to
retain the necessary migrator scope. The bootstrap has not been applied to any
database, so the original migration is revised; no upgrade migration or live
role changes are needed.

| Role | Purpose and effective boundary |
|---|---|
| `bi_analyst_reader` | SELECT on the ten gateway views, ten approved `analytics` dependencies and seven named `public` reporting dependencies; company-wide source SELECT RLS policies. Direct reads of those approved source relations are intentional. |
| `bi_analyst_state` | User-scoped application storage, rate counters and append-only audit; cannot change access grants or operational data. |
| `bi_analyst_view_owner` | Non-login owner of gateway views with explicit source SELECT privileges; no runtime membership, permanent CREATE, superuser or RLS-bypass privileges. |
| `bi_analyst_migrator` | Non-login owner of `analyst_query`, `analyst_state` and the seven state tables. Maintains analyst structures and provisions principals; no operational-table grants, shared-schema administration, role creation or runtime membership. |
| Existing platform administrator | Executes the bootstrap, creates roles, grants source SELECT access and installs source SELECT policies. Retains responsibility for shared database permissions. |
| Browser/Data API roles | No grants to the new analyst schemas. Authentication remains deferred and every data route remains disabled. |

The retained `bi_analyst_migrator` is an offline ownership role, with no password
or LOGIN. The bootstrap grants it only to the administrator running the script;
that administrator can use `SET LOCAL ROLE bi_analyst_migrator` within a reviewed
migration or access-provisioning transaction. Neither runtime role can assume it.
The `principal_admin` policy permits it to maintain access records. FORCE RLS
still applies to the other state tables; it receives no blanket history-reading
policy. As their owner, it can change their structures and policies, so it is
trusted to administer analyst state and must stay outside the API process.

It has no source-table SELECT/write grants or permission to administer existing
`public`/`analytics` objects, create roles/databases or bypass RLS. Source grants
and policies remain the platform administrator's responsibility. Gateway views
retain their separate non-login owner; gateway alterations likewise use the
platform administrator's view-owner authority. Future state tables or functions
require an explicit audit allowlist review before the API can start.

The `analyst_query` gateway remains the future query service's reporting
interface. Its ten views preserve the Phase 2 SQL through unchanged wrappers.
The reader now has explicit USAGE on `public` and `analytics`, so approved sources
are directly readable. This includes complete source-table rows, not just curated
columns. For example, raw `public.projects` can contain projects excluded by the
current legacy `reportable_projects` view; the gateway retains the existing
analytical population until the separate business-definition alignment is complete.

Nested invoker views check the original caller, even beneath owner-executed views.
The existing dependency SELECT grants and company-wide SELECT RLS policies are
therefore retained. Gateway views retain their non-login owner and security barrier.
See [PostgreSQL view security](https://www.postgresql.org/docs/current/sql-createview.html).

The legacy revenue diagnostic and optional archive gateway remain outside the
approved interface. No wildcard or future-object SELECT grants are introduced.

## Effective-privilege audit

Existing PUBLIC schema USAGE and database TEMP are accepted and preserved.
The migration does not change PUBLIC privileges on existing operational objects,
ETL roles or reporting roles. Revocations in the bootstrap apply only to the new
analyst schemas and objects.

The same checked-in SQL, `bi_analyst/permissions.sql`, runs at the end of migration
003 and during API startup, checking the reader, state writer, view owner and
scoped migrator.
Tests assert that its embedded migration copy stays identical. It checks effective
privileges, including grants inherited through PUBLIC, and reports role, issue and
object names when it finds:

- superuser, role/database creation, replication, RLS bypass, role memberships,
  or LOGIN on either offline owner;
- permanent schema/database CREATE or object ownership outside the approved
  owner scopes (the migrator's two analyst schemas/state and the gateway owner);
- table/column write, REFERENCES, TRIGGER or supported MAINTAIN privileges outside
  explicitly permitted state storage and ownership rights;
- unapproved table/column reads, sequence mutation, large-object update grants,
  privileged configuration-parameter grants or foreign-server access;
- executable application/extension functions or procedures without a reviewed
  definition, including SECURITY DEFINER and trigger functions.

The function review is deliberately independent of schema USAGE, volatility
labels and names alone. The two existing reporting dependencies
`project_placeholder_is_empty(jsonb)` and `excluded_project_ids()` are accepted
only when their exact stored body, signature, language, security mode, volatility
and fixed search path match the checked-in source. A changed definition needs
review. Other application or extension functions require an explicit reviewed
allowlist update; a harmless extension function may therefore block installation
until it is reviewed. The audit never automatically approves the deployed body.

PUBLIC privileges are additive: revoking a permission from just the analyst role
does not remove a PUBLIC grant. If PUBLIC already allows writes or an unsafe
function, this migration fails and rolls back; it does not silently revoke that
permission from existing consumers. Resolving that conflict requires a separate
owner decision, such as an isolated reporting database or a narrowly reviewed
permission change. Option A does not promise compatibility with unsafe existing
grants. See [PostgreSQL privileges](https://www.postgresql.org/docs/current/ddl-priv.html).

The runtime additionally verifies gateway ownership/security, exact runtime
connection roles, state RLS and restrictions on changing principal grants,
ownership fields and audit records. Source certification and complete-population
parity remain separate from permission verification.

### Limits of the read-only boundary

The reader is denied persistent operational DML and permanent CREATE by effective
ACLs, even if a client changes its default transaction mode. The application's
analytical operations additionally use explicit READ ONLY transactions with
statement/lock timeouts. TEMP permits session-local scratch objects; these are
not operational tables.

This is **not a universal sandbox for arbitrary SQL or stolen database credentials**.
The audit treats built-in PostgreSQL system functions as platform code. Some native
functions affect sessions or have other side effects, and a client controlling its
connection can change session defaults. For example, native large-object creation
requires the explicit read-only transaction boundary; withholding table-write
grants alone does not address it. PostgreSQL itself distinguishes read-only
transactions from universal side-effect prevention.
See [SET TRANSACTION](https://www.postgresql.org/docs/current/sql-set-transaction.html).

Consequently Phase 4 must admit only approved read statements and vetted functions,
enforce row/byte limits and retain explicit read-only transactions. No arbitrary
SQL execution endpoint exists now, and authentication remains disabled. Do not
enable real analytical query execution before those controls and source
certification pass. The database credentials remain exclusively on the server.

## Migration procedure

Migration `src/database/migrations/20261008_003_analyst_permissions.sql` is a
one-time bootstrap after migration 001. Migration 002 remains optional.
Apply the entire file in a single transaction using the existing platform
administrator, who must be able to create roles and source SELECT policies:

```text
psql --single-transaction --set ON_ERROR_STOP=1 --file src/database/migrations/20261008_003_analyst_permissions.sql
```

In the Supabase SQL editor, wrap the complete file in `BEGIN;` and `COMMIT;`.
Use `Run without RLS`: the script itself enables/forces RLS and installs the policies.
The private `schema_version` table intentionally uses restricted grants instead of
an RLS policy. Run on the isolated staging/test environment first. If the effective
privilege audit fails, retain its findings and review the named objects; do not
bypass the audit or rerun only fragments of the migration.

The bootstrap creates four roles, initially NOLOGIN, without passwords.
Provision LOGIN and independent passwords only for the reader and state writer
through the normal secret-management workflow. Grant database CONNECT explicitly
if required. Keep the migrator and view owner NOLOGIN. Do not give Render
administrator, migrator or view-owner credentials.

Keep `analytics`, `analyst_query` and `analyst_state` outside Supabase's exposed
Data API schemas. Do not grant the runtime roles to browser roles. Provision
principals through an administrator transaction using the scoped migrator when
trusted identity is implemented; both access flags default to false. Increment `permissions_version` on every
access change. The state-role session setting prevents accidental cross-user reads;
it does not protect against compromise of the trusted state-role credential.

## Connection and Render configuration

Use [the independent environment example](../services/bi_analyst/env.example).
The service does not load the root `.env`, and rejects privileged or mismatched
database roles. Remote DSNs require `sslmode=verify-full`; supply the appropriate
trusted CA with `sslrootcert` when the platform certificate is not in the normal
trust store. Only explicit loopback test connections may omit TLS.

Use a direct connection, or a Supabase session pooler on port 5432. Session-pooler
usernames may be `bi_analyst_reader.PROJECT_REF` and
`bi_analyst_state.PROJECT_REF`; the underlying database roles are still checked at
startup. Verify IPv4/IPv6 reachability and TLS from the target Render environment.
Transaction-pooler port 6543 is rejected; driver and future checkpointer compatibility
has not been established. See [Supabase connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres).

Each process has separate bounded reader/state pools, default maximum two
connections each. The configured replica count times the sum of pool maxima must
fit the connection budget explicitly reserved after ETL/other services. The service
uses one Uvicorn worker. Account for deployment overlap as well as steady replicas
when reserving database capacity. Pool waits, pending requests, SQL statement time
and lock waits are bounded. Connections are released at the end of each short
operation; no connection is held while waiting for user input.

The [Render Blueprint](../services/bi_analyst/render.yaml) points only at this
package, uses the independent lockfile, configures a separate service and disables
automatic deploys. Select that Blueprint path explicitly in Render. Set secrets
and the exact trusted frontend origins there; CORS is not authentication. The
configuration follows the [Render FastAPI entrypoint guidance](https://render.com/docs/deploy-fastapi)
and [Blueprint reference](https://render.com/docs/blueprint-spec). Production plan
size and replica count still require measured load and budget review.

To install and start independently from `services/bi_analyst`:

```text
python -m pip install -r requirements.lock
python -m pip install --no-deps --no-build-isolation .
python -m uvicorn bi_analyst.api:application --factory --host 127.0.0.1 --port 8000 --workers 1 --no-access-log --no-proxy-headers
```

Only health routes are usable until identity is implemented. Secrets must be
provided through process environment/secret storage. Application rollback leaves
the additive schemas and audit data intact; disable the service or revoke its
login access without dropping tables or changing ETL data.

## Verification and remaining release gates

The new isolated tests are under `services/bi_analyst/tests/api`. Unit tests verify
configuration restrictions, CSV safety and import isolation. Integration tests
create a random disposable database on an explicit loopback test cluster, apply
the real Phase 2/3 SQL, enable source RLS and connect as real restricted roles.
They refuse existing analyst roles and remove only their own test database/roles.
Do not run parallel copies on the same cluster because PostgreSQL roles are global.

```powershell
$env:BI_ANALYST_TEST_DSN = 'host=127.0.0.1 port=55439 dbname=postgres user=postgres connect_timeout=15 sslmode=disable gssencmode=disable'
& .\report.venv\Scripts\python.exe -m pytest services/bi_analyst/tests -q
```

The checks cover default-denied identity, company scope, cross-user histories,
follow-ups, cancellation, resume and exports, grant revocation/version changes,
rate limits across instances, restart persistence, audit records, input bounds,
CORS, approved direct source reads, forbidden operational writes/functions, future-object
denial, RLS and permission drift. Migrator tests exercise analyst DDL and principal
provisioning, deny operational DDL/DML and role escalation, and reject runtime
membership or grants outside the migrator's scope. Synthetic ETL/Power BI roles retain their effective
ACLs and continue to update/read their existing reporting tables. PUBLIC schema
USAGE and database TEMP remain unchanged.
Historical Phase 2 parity remains separate evidence for the unchanged candidates.

Option A verification on 8 October 2026: **142 analyst tests passed**, with no
skipped tests, including the real PostgreSQL permission tests and the full existing
Phase 1/2 regression suite. The wheel built successfully and its packaged
permission-audit SQL matched the source exactly; `git diff --check` passed.
The full run used a fresh workspace `--basetemp` directory because the existing
Windows pytest temporary directory had incompatible permissions. These results
establish local code and synthetic-database behavior, not production certification.

Production deployment, environment-specific effective-privilege review, source certification,
identity implementation and measured Render/Supabase connectivity/capacity remain
open. This delivery neither modifies the frozen evaluation dataset nor deploys
changes to Supabase, Monday or Render.
