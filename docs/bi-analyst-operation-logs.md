# Following an analyst question in backend logs

Open the analyst backend service in Render, select **Logs > Live tail**, and
submit or retry a question. This logging change requires a backend deployment;
it does not require a database migration, frontend deployment or new environment
variables.

## Correlation

The response to `POST /v1/conversations/{conversation_id}/messages` includes
`run_id`. Search Render logs for that UUID to follow one processing attempt.
Retrying an interrupted question creates a new run ID. A conversation can
contain multiple runs.

The HTTP response's `X-Request-ID` is generated by the server. The submission's
`http_request` log includes both this request ID and the accepted run ID.
Background workflow, model and query logs inherit the submitting request ID.
Resuming a clarification inherits the resume request's new ID. Other status or
stream requests have their own request IDs and include the run ID from their
validated route. Client-supplied request IDs are not trusted.

## Operation events

Workflow, model and metric query operations emit `analyst_operation` events with
`phase: start` and `phase: end`. Each pair has a unique `operation_id`, so repeated
calls in the same run remain distinguishable. For example:

```json
{"event":"analyst_operation","phase":"start","stage":"model","operation":"interpret","operation_id":"e1486790-0fd1-43e3-a331-5040a458c6b7","run_id":"48eae5b8-c6e7-4b85-a63d-ce3e794f1251","request_id":"4dd23665-9312-4e8c-a302-f0b9e042cacf","attempt":1}
{"event":"analyst_operation","phase":"end","stage":"model","operation":"interpret","operation_id":"e1486790-0fd1-43e3-a331-5040a458c6b7","run_id":"48eae5b8-c6e7-4b85-a63d-ce3e794f1251","request_id":"4dd23665-9312-4e8c-a302-f0b9e042cacf","attempt":1,"outcome":"failed","error_code":"model_unavailable","duration_ms":184}
```

| Stage | Operation | Meaning |
|---|---|---|
| `workflow` | `run_workflow` | One background execution segment, including cleanup |
| `model` | `interpret` | Identify the question's metric family |
| `model` | `plan` | Prepare a structured metric request or clarification |
| `model` | `presentation` | Select evidence claims and presentation |
| `query` | `metric_query` | Execute the validated metric request |

`attempt` starts at 1 for each model invocation and increments on its existing
bounded retry. Each retry has its own operation ID. A later invocation or resumed
execution starts at attempt 1 again. Workflow and query operations use attempt 1;
this field does not count the user's retries of a question.

Workflow, model and query end events retain the original `stage`, `outcome` and `duration_ms` fields.
They add a fixed `error_code`, or `null` on success. Examples include
`model_authentication_failed`, `model_timeout`, `metric_query_timeout`,
`run_timeout`, `permissions_changed`, `invalid_evidence`, `execution_cancelled`
and `execution_interrupted`. Unrecognised exception codes become the fixed
stage fallback, such as `model_failed` or `workflow_failed`. Raw exception
messages are never logged. Model transport timeouts remain retryable and are
now distinguished from other provider availability failures.

The existing HTTP operation summary is still emitted at response preparation;
it has `operation: http_request`, `phase: end` and no paired operation ID. An
HTTP 202 means submission was accepted. Its duration is separate from the
background workflow duration, and an SSE HTTP summary does not measure the
stream's full lifetime.

## Reading failures

A start event shows an operation was entered. A matching end shows its outcome
and elapsed time. If the process is forcibly terminated, an end event may never
be emitted; compare unmatched starts with platform restart/deploy messages and
the saved `/v1/runs/{run_id}/workflow` response. Workflow logs describe the
execution outcome; cancellation, permission changes or lease expiration may
already have established a different saved terminal state.

The authenticated `/v1/runs/{run_id}/events` stream remains the source of detailed
progress stages and validated answers, including business values for the authorised
run. Backend logs exclude raw prompts, SQL, business result rows and model output.
IDs are restricted to canonical
UUIDs, operation names and error codes are allowlisted, and task-local context is
restored after failures, retries and cancellation.

Prometheus metrics retain their existing bounded stage/outcome labels. Only end
events increment operation counters and latency histograms. Run, request and
operation IDs appear in logs only, so this change does not create per-run metric
series.
